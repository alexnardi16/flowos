# FlowOS implementation status

## Implemented

- Mobile-first Expo Router application
- Unified Commitment domain model
- Today, Plan, Inbox, Profile, Capture and Focus screens
- Natural-language interpretation with a Supabase Edge Function
- Local fallback parser when the backend is unavailable
- Supabase passwordless authentication
- Persistent authentication sessions
- Supabase repository with Row Level Security schema
- Offline persistence and mutation queue
- Local notifications
- Daily summary notification at 07:30 local time, with automatic Google Calendar/Tasks sync beforehand, missed-summary recovery on app foreground, duplicate prevention, a dedicated notification log, and a Notifiche settings screen
- Per-event reminders 10 minutes before start, grouped due-soon/overdue task notifications, and app badge count (ReminderEngine)
- Automatic replanning (missed slots, conflicts with fixed events), energy-aware scheduling within real weekly availability windows, and rule-based planning suggestions (ReplanEngine + extended PlanningEngine)
- Today's weather in the daily summary (Open-Meteo, device location via expo-location)
- All-day events handled by calendar day everywhere (no more 2am display bug, no longer block the whole day in auto-planning), recurring events/tasks/reminders with series-vs-occurrence deletion, and a Google-Contacts (birthdays) event filter in Oggi/Piano
- Device calendar event creation
- EAS Build and EAS Update profiles
- GitHub Actions TypeScript validation

## Known gaps found while implementing Sprint 1

- **RESOLVED**: `supabase/functions/google-workspace/index.ts` is now committed (Alex provided the source). `google-delete-item` is still not in the repo — recommend committing it too the same way. **Deploying the updated `google-workspace` function is a manual step, not automatic**: run `supabase functions deploy google-workspace` (or redeploy from the Supabase dashboard) after pulling this change, or the fixes below won't take effect in production.
- **The `google-workspace` Edge Function changes (all-day marker, recurring-series capture, `sync-delete-series`, RRULE creation) were checked for TypeScript syntax validity (esbuild) but never run** — there's no Deno runtime or Supabase project access in this environment to execute or deploy it. Verify with a real sync after deploying, especially the Google Contacts `eventType: "birthday"` assumption, which is documented but untested against live data.
- The daily summary background task (`lib/backgroundSyncService.ts`) uses `expo-background-task`, which is opportunistic on both Android (WorkManager) and iOS (BGTaskScheduler): the OS decides when it actually runs, not FlowOS. The 07:30 notification's *delivery time* is still exact because it is a native OS calendar trigger; only its *content freshness* depends on whether a background sync managed to run beforehand. The in-app recovery check on foreground does not have this limitation.
- `lib/diagnostics.ts` only persists to `window.localStorage`, so on native builds (iOS/Android) it silently records nothing — the in-app "Logger" section under Io only ever shows data on the web build. Not fixed as part of this sprint; the new `lib/notificationLog.ts` uses AsyncStorage instead and works on every platform.
- The grouped due-soon/overdue notifications only re-fire when the underlying set of task ids changes (content-hash dedup), not once per day regardless. An overdue task that never changes will not keep re-notifying every morning — intentional, to avoid nagging, but worth knowing if the expectation was a daily repeat.
- **Sprint 3 native widgets/companions were only partially built, and only the iOS widget at that.** This environment has no Xcode, no Android Studio, and no way to run EAS Build (api.expo.dev is outside the sandbox's network allowlist), so nothing native could be compiled or visually verified here — only TypeScript could be written and typechecked.
  - iOS widget: scaffolded with the official `expo-widgets` library (`widgets/TodayWidget.tsx`, wired into `lib/widgetSync.ts`). Typechecks against real library types, but has never been run. **Verify with a real iOS development build before shipping.**
  - Android widget: not implemented. Recommend `react-native-android-widget` — it renders JSX to native RemoteViews via a config plugin, so it's buildable without hand-written Kotlin, but its component API needs to be checked against current docs before writing it (only shallow secondary-source knowledge of it going into this sprint).
  - Wear OS companion: not implemented. This is a separate native Kotlin module using the Wear OS Data Layer API to talk to the phone app — real native engineering, not a config-plugin shortcut.
  - Apple Watch companion: not implemented. Same situation on the other platform — a separate watchOS target in Swift/SwiftUI, using WatchConnectivity to talk to the phone app.
  - Recommend doing the remaining three with a local Claude Code session (or a mobile engineer) on a machine that actually has Xcode/Android Studio, where the native build can be compiled and tested as it's written — the same rigor Sprint 1/2 had here, just with the right tools for native code.
- **Sprint 4's "suggerimenti automatici dell'IA" are rule-based heuristics, not an LLM call.** Wiring real AI suggestions in would need a new Supabase Edge Function (like `interpret-commitment`) calling a model — writeable here, but not deployable or testable end-to-end without Supabase project access. The current gap list already flags that even the *existing* Google-sync edge functions aren't committed to this repo; adding a new undeployed one would only make that worse until that's sorted out first.
- **Sprint 5: only weather was actually built.** Traffic/travel-time (`lib/travelTime.ts`) is a documented stub, not an implementation — it needs a billed Google routing API key that hasn't been provided, plus geocoding for commitment locations (currently free text). Android Auto and CarPlay were not started at all: both are native car-integration frameworks (Android's Car App Library in Kotlin, CarPlay's framework in Swift), the same category of work as the Wear OS/Apple Watch gap in Sprint 3 — needs Xcode/Android Studio and should go through a local Claude Code session or a mobile engineer, not this sandbox.
- **GitHub Codespaces has no Android SDK by default.** `eas build --local` and `expo run:android` both fail with "SDK location not found" until one is installed. `.devcontainer/devcontainer.json` + `.devcontainer/setup-android-sdk.sh` fix this for any *new* Codespace (or an existing one after "Rebuild Container"). For a Codespace already running, run `bash .devcontainer/setup-android-sdk.sh` once manually. The script pins `platforms;android-36`, `build-tools;36.0.0` and `ndk;27.1.12297006` to match what this project's Gradle build actually requests — re-check those version numbers against a build log if this ever starts failing again after an SDK bump.
- **JDK 22+ breaks CMake-based native modules (expo-updates, react-native-worklets) with an unhelpful error.** The task fails with only `WARNING: A restricted method in java.lang.System has been called` as the reported cause — this is JEP 472's native-access restriction, unrelated to any app code, and it's a known issue across many native Android projects (react-native, react-native-vision-camera, etc. all hit the identical message). Two mitigations are in place: `.devcontainer/devcontainer.json` pins JDK 17 (the traditional, still-safe choice for Android tooling) instead of a newer default, and `plugins/withNativeAccessJvmArgs.js` — a local Expo config plugin — appends `--enable-native-access=ALL-UNNAMED` to `org.gradle.jvmargs` on every `expo prebuild`, so even a build machine that does use a newer JDK (an EAS cloud builder, someone's own laptop) won't hit this.
- **A local build on a memory-constrained machine (default GitHub Codespace) OOM-kills the Kotlin compile daemon or the Gradle daemon mid-build**, surfacing as "Connection to the Kotlin daemon has been unexpectedly lost", "Gradle build daemon disappeared unexpectedly", or "Broken pipe" — all symptoms of the OS killing a JVM process for memory, not a real build error. Restricting to a single ABI (`ORG_GRADLE_PROJECT_reactNativeArchitectures=arm64-v8a`) helps but isn't sufficient on its own. `plugins/withNativeAccessJvmArgs.js` now also sets `kotlin.compiler.execution.strategy=in-process` (runs the Kotlin compiler inside the Gradle daemon's JVM instead of spawning a second daemon process — the single biggest lever for peak memory) and caps `org.gradle.workers.max=1` / disables `org.gradle.parallel`. If local builds still OOM after this, the remaining fix is a bigger Codespace machine type (Codespace settings → "Change machine type"), not more code changes — a full native Android release build has a real minimum memory footprint that no amount of Gradle tuning gets below indefinitely.
- **`expo-notifications` and `expo-task-manager`/`expo-background-task` are not implemented on web** — calling their scheduling/registration APIs there throws "is not available on web". Every call site (`lib/notificationService.ts`, `lib/reminderEngine.ts`, `lib/backgroundSyncService.ts`) now checks `NOTIFICATIONS_SUPPORTED_HERE` / `Platform.OS === 'web'` first and no-ops with a log entry instead of throwing. This was the root cause of the unhandled-promise-rejection crashes seen in the web build, and very likely a contributor to the "previous sync interrupted" message (a crash mid-flow could leave the server-side sync status stuck at `syncing`). `lib/backgroundSyncService.ts`'s reminder/replan calls are now also wrapped so a failure there can never abort the daily-summary or Google-sync flow that called them.
- **`Alert.alert` shows nothing on web** in this project's react-native-web setup — buttons wired to it (the notification test button, several Google Workspace error dialogs) looked like they did nothing when run in a browser. `components/ui.tsx` now exports `showAlert()`, which falls back to `window.alert` on web; all call sites in `me.tsx` and `notifications-settings.tsx` were switched to it.
- **Never received the daily notification, even after everything above was fixed:** two separate reasons, not one bug. (1) Until the crash fixes above, the whole notification pipeline was silently breaking on every run wherever it happened to be tested from the web build. (2) Even with real native notifications working, **web browsers cannot receive OS-level scheduled notifications the way `expo-notifications` delivers them on iOS/Android** — that would need an entirely separate implementation (a Service Worker + the Web Push API + VAPID keys + a push endpoint), which does not exist in this project. Testing the daily 07:30 notification only becomes meaningful once a native build is actually installed on a phone — see the Codespace/JDK/memory fixes above for where that stands.
- **The three items previously blocked on the missing Edge Function source are now implemented, both server- and client-side** (Alex provided `google-workspace`'s source, now committed — see the resolved gap above). Specifics:
  - **All-day events at 02:00 instead of midnight**: root cause confirmed in `pullCalendarPage` — all-day events were stored as `${date}T00:00:00.000Z`, which is correct in absolute terms but shifts to 02:00 in Europe/Paris CEST (UTC+2) once read with local getters. Rather than guess a timezone server-side, the fix marks these `allDay: true` in `ai_metadata` and makes the client always read/format/compare them with UTC getters (`lib/allDayDate.ts`) — the calendar day Google reports, independent of viewer timezone. This also surfaced a second, more serious bug not explicitly reported: an all-day fixed event has `duration_minutes: 1440`, which was blocking the PlanningEngine from scheduling *any* flexible task on that entire day (`lib/scheduler.ts`'s overlap check treated it as an all-day busy block). Fixed alongside the display issue.
  - **Recurring items**: Google Calendar events are already expanded into individual instances server-side (`singleEvents: true`), each carrying `recurringEventId` — now captured into `ai_metadata.googleRecurringEventId`. Deleting a single occurrence already worked (existing delete-by-`external_id` logic); a new `sync-delete-series` action was added to the Edge Function for deleting the whole series (calls Google's DELETE on the master event, then marks every local commitment sharing that series id as deleted). The Piano screen's "Gestisci" now offers both choices for recurring items. Google Tasks has no native recurrence concept in Google's own API — locally-managed recurring tasks/reminders (`lib/recurrence.ts`) materialize their next occurrence client-side when marked done, entirely independent of Google. Creating a *new* recurring event now sends a real RRULE string to Google (`eventBody` in the Edge Function, `toRRuleString` client-side); a "Ripeti" picker (non ripetere / ogni giorno / settimana / mese) was added to the Aggiungi screen.
  - **Google Contacts event filter**: Google Calendar's `eventType` field (captured as `ai_metadata.googleEventType`) distinguishes `"birthday"` from `"default"` events — this is the officially documented API field for exactly this, but hasn't been verified against real synced data yet, since that requires a live Google account. The Piano and Oggi screens both got a 3-way filter (tutti / solo contatti / escludi contatti).
